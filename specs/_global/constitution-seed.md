# Constitution Seed — visc-line

> Architectural principles and coding conventions for the visc-line library.
> Generated by `/reverse-spec` Phase 4-1.

## Source Code Reference Principles

### Same Stack Rebuild

Since this is a **Same Stack rebuild** (TypeScript + D3.js), the existing architecture patterns are preserved:

- **Functional rendering**: Each component uses D3 data join for idempotent DOM updates
- **Fluent API**: ChartInstance uses method chaining for feature toggles
- **CSS variable theming**: Visual attributes via CSS custom properties
- **Curve preset system**: 18 predefined D3 curve factories

### TypeScript Conventions

- Strict mode enabled (`"strict": true` in tsconfig)
- No unused locals or parameters
- Functional patterns preferred (no classes for components)
- Generic types for data flexibility

## Extracted Architecture Principles

### AP-001: Idempotent Rendering

**Principle**: All renderers must be idempotent — selecting existing DOM nodes by class/attribute before appending.

**Evidence**: All component renderers use D3 `.data([null]).join()` pattern.

**Implication**: Re-renders never duplicate elements; they update existing ones.

---

### AP-002: CSS Variables First

**Principle**: CSS variables (`var(--vl-*)`) are used for all visual attributes — no hardcoded inline style values in renderers.

**Evidence**: `applyThemeCssVars()` writes CSS vars before SVG exists; `getComputedStyle()` reads them when D3 APIs require numbers.

**Implication**: Theme changes don't require code changes.

---

### AP-003: Functional Composition

**Principle**: Charts are composed from small, focused functions rather than large component classes.

**Evidence**: Separate renderers for SVG, bounds, line, points, axes, grid, title, legend.

**Implication**: Each function is testable in isolation.

---

### AP-004: Data Validation Upfront

**Principle**: Invalid numeric values are filtered before rendering to prevent D3 errors.

**Evidence**: `processNumericData()` and `isValidNumber()` in dataWrangling.mts

**Implication**: Axes and lines only render valid data points.

---

### AP-005: Single Responsibility

**Principle**: Each module has one job:
- `services/scales.ts` — scale creation
- `services/dataWrangling.ts` — data processing
- `services/layout.ts` — dimension calculations

**Evidence**: Clear separation in src/services/

## Technical Constraints

### TC-001: Browser-Only Platform

- **Constraint**: Library is browser-only (UMD output via tsdown)
- **Implication**: No Node.js-specific APIs, no file system access

### TC-002: D3 Peer Dependency

- **Constraint**: D3 v7.9.0 is a peer dependency (not bundled)
- **Implication**: Consumers must provide D3; library assumes D3 APIs are available

### TC-003: tipviz Bundled Dependency

- **Constraint**: tipviz is forced into bundle (alwaysBundle in tsdown.config)
- **Implication**: tipviz functionality is included in UMD output

## Coding Conventions

### Function Naming

| Pattern | Example |
|---------|---------|
| CamelCase functions | `createChart`, `renderLine`, `mergeTheme` |
| PascalCase types/components | `ChartInstance`, `ChartConfig`, `ProcessedSeries` |
| UPPER_SNAKE_CASE constants | `CURVE_PRESETS`, `DEFAULT_MARGINS` |

### Boolean Naming

Prefix with `is`/`has`/`can`/`should`:
- `isValidNumber`
- `hasAxes`
- `areLegendOptionsEqual`

### D3 Usage Patterns

1. **Selection**: `select(container).selectAll('svg').data([null]).join('svg')`
2. **Data Join**: Always use `.data()` with join for idempotent updates
3. **Scales**: Configure domains, ranges, then `.nice()` for cleaner ticks

### Error Handling

- Throw Error with descriptive message on invalid inputs
- Use `ensureActive()` guard for disposed chart operations
- No silent failures — validate upfront

## Recommended Development Principles

### Test-First

- All new functions require unit tests
- Use Vitest with jsdom environment
- Coverage threshold: all src/**/*.mts files

### Think Before Coding

- Document function behavior with JSDoc
- Specify input validation requirements
- Note side effects (module-level caches, DOM mutations)

### Simplicity First

- Prefer pure functions where possible
- Avoid classes for component state
- Keep render functions focused on single responsibility

### Surgical Changes

- Modify only the necessary files for a change
- Update tests when behavior changes
- No large refactors without design review

### Goal-Driven Execution

- Each PR addresses one feature or bug
- Commit messages describe the why, not just the what
- Demo-ready: working example for each feature

## Project-Specific Recommended Principles

### Domain-Driven: D3 Interoperability

**Principle**: All chart components must work with standard D3 scale and shape APIs.

**Evidence**: `createScales()` returns AnyScale union type compatible with D3; renderers accept D3 selections.

**Recommendation**: All new components should follow D3 join patterns and work with standard D3 selections.

---

### Architecture-Driven: Render Pipeline Contract

**Principle**: The chart render sequence (BL-CF-001) is a hard contract. Components must execute in order.

**Evidence**: chartRender.mts orchestrates the exact sequence; each renderer assumes prior steps completed.

**Recommendation**: Any new renderer must be added to the official sequence in chartRender.mts.

---

### Quality-Driven: Type Safety for Chart APIs

**Principle**: Public APIs must have complete TypeScript types. No `any` casts on public interfaces.

**Evidence**: All exports from index.mts have explicit type annotations; strict mode enabled.

**Recommendation**: New exported functions must include JSDoc with @param and @returns types.

---

### Quality-Driven: Test Coverage for Data Paths

**Principle**: Data processing functions (isValidNumber, processNumericData, getMultiSeriesExtents) require 100% branch coverage.

**Evidence**: dataWrangling.mts has dedicated test file with edge case coverage.

**Recommendation**: Boundary conditions (NaN, Infinity, null, undefined, empty arrays) must all be tested.
